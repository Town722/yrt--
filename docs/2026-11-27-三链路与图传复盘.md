## 1. 无屏 RK3588 从临时联网到开机直连

**现象。** 网桥已配对、有线网口亮灯，Windows 一度只得到 `169.254.x.x`，无屏板端也无法直接查看地址。对网桥重新配对或猜测 SSH 端口，无法区分链路、地址分配和服务监听三个层次。

**定位。** 在真实有线网卡上用 PktMon 只看 ARP 和 DHCP。抓包前先确认变量与输出路径，一次失败来自 `--file-name` 后没有值。指定实际日志位置后，抓包可见板端请求穿过网桥，却没有得到正常应答。启用临时 DHCP 并重新插回板端网线后可重新进入板端。另一次早期记录曾出现板端已使用 DHCP 地址而 TCP 22 主动拒绝，说明发现地址后还要验证服务监听。

**解决。** 对桥接段持久设置 Windows 有线网口 `192.168.137.10/24` 和 RK3588 `eth0` `192.168.137.246/24`，网桥接口的默认网关保留为空，板端蜂窝网口仍可持有默认路由。Windows 没有路由器和临时 DHCP 的条件下重启板端，SSH 登录和 `eth0` 地址均复测通过。网桥管理网段与实验网段分开，后续无线状态采集使用只读请求，保持用户要求的网桥参数原样。 [早期抓包记录](headless-network-diagnosis-2026-11-05.md) · [固定地址与重启实测](wifi-bridge-first-test.md)

## 2. 三链路的数据口径、真机基线与校时

- **组包和收包。** 电脑为每条逻辑指令编码一个 20 字节帧，携带实验编号、序号、指令值和 CRC32。三路独立排队发送同一逻辑指令的副本。板端仅在序号增大时更新模拟状态，所有通过解析的重复和晚到副本仍入日志。提交成功和板端收到分别统计。绿色是采用，黄色是延迟到达的副本，红色是旧序号晚到。第一阶段使用普通发包，用户可手动排除链路，后续九包判决另行设计和验证。
- **室内基线。** 1 Hz 三路全开时各收 12 份，共 36 份，逻辑更新 12 次。构造 `1、3、2、4` 后采用 `1、3、4`，序号 2 晚到仍有记录。地面站停发网桥后，LoRa、4G 各收到 5 份，共采用 5 条指令。这是静态并发和按链路停发验证。 [真机基线与后续场景](three-link-baseline.md)
- **串口与 4G 网卡。** CH340 和移远 AT 串口重插后号码可变，Windows 改为枚举 USB 标识，每次打开前重新识别，多设备时可手动选。`WinError 10022` 排查转向网卡绑定，不固定使用上次接口索引，按当前配置的 4G 本地 IP 获取 Windows 接口索引。另一次故障中 EC200A 能注册 LTE，但 RNDIS 无公网数据连接，AT 查询后按模块命令拨号，收到联网状态，再以两端短消息验证数传。 [桌面与串口设置](../deploy/three-link/README.md)
- **两个时差。** 相对首达差用车端同一个单调时钟比较同序号的副本。发送提交到接收差用 Windows 高精度时钟、板端单调时钟以及每轮 SSH 四时间戳校准。系统日期偏差、实验中板端重启、SSH 未校准、以及小于校准不确定度的估值各自有不同处理。界面把无效负估计和低于精度的估计标为校时误差，CSV 留原始估计、校准 RTT 和状态。旧日志没有足够的信息时，保持无单程时延结论。板端另外做过 NTP 同步修正，系统时间与实验单调时钟的用途分别记录。 [帧格式和时差合并](../deploy/three-link/fusion.py)
- **无线质量。** 早期按每条链路自己的 RSSI 或 RSRP 绝对值做固定参考点归一化，保留原值和来源，得分独立于同轮其他链路。后续按实际界面要求移除接收页的无线量和 0–1 显示。11 月 20 日部分高频轮 LoRa 丢包严重，在没有 4G 应用发送的轮次也有丢包，无法由并发日志直接证实 4G 射频淹没 LoRa。11 月 6 日近距离强信号对照也未检出明显变化，弱信号边缘仍需控制变量复测。 [无线质量和丢包复核](radio-quality-2026-11-20.md) · [射频共存数据](coexistence-2026-11-06/README.md)

## 3. 手机地面站从界面预览到实验闭环

**交互和部署。** Windows 使用原生 EXE，手机使用竖屏 HTTPS 页面。两端统一视觉、链路勾选样式和实验入口。实验编号按年月日和分钟生成，同一分钟加序号，兼容旧实验。手机同一逻辑指令的不同副本统一显示 `#序号`。桌面保留导出 CSV，手机侧保留现场需要的启停、参数、接收明细和历史回放。摄影站已有根路径，控制页挂在 `/yrt-mobile/`，接口走同源 HTTPS，网关监听 ECS 回环口。网关使用独立的手机、电脑、车端令牌。

- **网桥取数。** 电脑经 SSH 实时读车端日志，随后提交已合并的记录，手机边测边看。实验结束补齐整轮，历史归档可在电脑离线后查看。
- **4G 取数。** 实验结束后由电脑向网关申请该轮日志，板端仅上传指定实验，电脑合并发送记录并计算时差，手机读取同一份归档。批量上传期间车端代理仍保持心跳。这里的 4G 取数是实验日志路径，车载视频则是单独的数据流。
- **部署故障。** 一次 Workbench 会话只能由用户在服务器终端完成安装，客户端报车端令牌长度错误也发生在正式部署之前。工具改为本机从剪贴板读取车端令牌后，板端服务启动并报告通过 LTE 鉴权。安装期遇到的 `HTTP 502` 属于当时的中转失败，现有记录不足以确认每一次 502 的单一根因。`invalid link` 则能复现到前端选择器误把没有 `data-link` 的选中控件算作实验链路。限定为 `input[data-link]:checked` 后解决。看到 `HTTP 409` 时应读对应接口的响应和设备状态，代码中有电脑或车端代理离线等明确冲突原因，单凭界面的在线徽标无法判断是哪一请求失败。
- **历史记录。** 早期下拉选项出现十六进制标识，看起来像乱码。旧内部编号有实际用途，页面优先显示用户可辨认的实验编号与日期时间。同一份历史记录可以查看副本和按链路回放。实时和归档状态区分开，避免刚收到原始车端日志时把尚未由电脑合并的结果当成最终记录。 [手机网页](../ground-station/mobile-control-preview.html) · [网关与角色](../deploy/mobile-gateway/README.md) · [历史补发程序](../deploy/three-link/publish_history.py)

## 4. LoRa 延迟怎么一步步定位

### 先清除已知的人为等待

HD-M805 切到模式 0 后，包尾 RSSI 不再追加。板端如果仍按模式 1 等尾字节，在特定读包路径会多等约 200 ms 的串口超时。确认工作模式与 `lora_rssi_suffix` 一致后重新测量。厂商设置程序读到两端 UART 为 9600，空速对照涉及 9600 与 19200 bps。UART 波特率和空中速率是两个参数。调高空速后，用户在原地面站观察到约 150 ms 的量级，仍有明显延迟，所以继续拆分检查。SSH 的 PTY 申请失败、Windows PowerShell 引号错误和本地 GBK 解码异常曾干扰修改操作，修正后以板端配置和服务运行状态核验。 [模式配置与接收器](../deploy/three-link/README.md#安装接收服务)

11 月 26 日原地面站的两轮 LoRa 独立测试进一步量化了问题。只比较逻辑指令，去掉起止帧，时延口径是 Windows 发送提交到 RK3588 收到。

| 实验编号 | 频率 | 收到 / 提交 | 时延中位数 | P95 |
| --- | ---: | ---: | ---: | ---: |
| `20261126-2155` | 1 Hz | 20/20 | 192.9 ms | 215.3 ms |
| `20261126-2156` | 2 Hz | 200/200 | 185.6 ms | 236.3 ms |

### 再绕开 RK3588、4G、网桥和跨机时钟

开发 [LoRa 同机对测](../deploy/three-link/lora_bench.py)，把两只 LoRa 接到同一台 Windows，用同一计时器记录 `write` 开始到首字节、到完整帧、以及进程读取首末字节的跨度。对测帧带独立标识、序号和 CRC。再加随机发包间隔、不同包长、CH340 本地回环及换 USB 口对照。以下是逐帧 CSV 的 P95 和中位数，单位为毫秒。无线往返方向分别测试，表内都是单向写入至收齐。

| 对照 | 帧长 | 收齐 / 发送 | 中位数 | P95 |
| --- | ---: | ---: | ---: | ---: |
| 初次无线 COM3 → COM17 | 20 B | 49/50 | 159.77 | 243.61 |
| 初次无线 COM17 → COM3 | 20 B | 50/50 | 154.74 | 232.11 |
| 随机间隔无线 | 20 B | 36/36 | 182.68 | 235.17 |
| 随机间隔无线 | 40 B | 36/36 | 183.64 | 239.38 |
| 随机间隔无线 | 80 B | 36/36 | 346.14 | 384.24 |
| 第一块 CH340 回环 | 20 B | 36/36 | 22.80 | 22.98 |
| 第一块 CH340 回环 | 40 B | 36/36 | 43.43 | 43.77 |
| 第一块 CH340 回环 | 80 B | 36/36 | 85.18 | 85.33 |
| 第二块 CH340 回环 | 20 B | 36/36 | 22.64 | 22.88 |

串口写入调用本身只有约 0.1–0.2 ms。9600 8N1 下，20 字节一次 UART 的理论串行时间约 20.8 ms，单板回环约 23 ms 与之吻合。无线对照同长度比回环多约 160 ms，扣去额外一次 UART 后仍相差约 139 ms。40 和 80 字节的首末字节读取跨度在有线与无线几乎相同，说明 Windows 读取方式会把字节成批交给应用，但无法解释额外的 100 多毫秒。 [LoRa 对照数据](2026-11-27-LoRa对照数据.md)

### 最有价值的线索是周期和断电对照

1. **发包时刻打散后，接收时刻仍锁在约 100 ms 的节拍上。** 更换接收 USB 口后无线组复现，COM22 和 COM23 的典型拟合周期约 100.19 ms 与 100.03 ms。COM22 两轮中 95% 首字节相对拟合节拍的偏差不到 0.7 ms；把程序读取超时从 50 ms 改为 13 ms，节拍仍存在。有线回环没有该节拍。
2. **重启一个端点再对比相位。** 第一次记录前后相隔数分钟，漂移与相位重置很难区分。改为连续双向采样并读取 Windows 设备到达记录后，确认实际重新插入的是 COM23，COM22 一直在线。COM23 作接收端时，断电前后首字节样本隔约 17.8 秒，约 100 ms 周期的相位偏移约 48 ms。另一方向未看到同等幅度的突变，但间隔较长，证据较弱。
3. **结论与限制。** 现有对照把问题定位到无线模块链路，尤其指向接收端的处理或串口输出调度。断电同时重启了该端 LoRa 与转接板，所以无法把这一轮相位变化直接定为某段固件代码。物理电平可以再用双通道逻辑分析仪对齐发射模块 RXD 和接收模块 TXD。Windows USB ETW 跟踪因本地会话缺少管理员权限未启动。现有实测足以说明这对模块在当前配置下不符合本项目对低延迟遥控的要求。

## 5. 车载图传从可用到低延迟持续流

| 版本 / 基线 | 采集、编码与传输 | 实际证据 |
| --- | --- | --- |
| 7 月无人船旧基线 | Astra Pro 输入 1280×720 MJPEG 30 fps。RK3588 MPP 编码 H.264 720p、20 fps，约 1.2 Mbit/s、GOP 10。TCP 连续传输 MPEG-TS，ECS 中继到低延迟模式的 QGC。 | 旧手册记录可看图传及经 LTE 工作，没有可用于这次同口径对比的持续帧率或端到端时延测量数字。 |
| v27 网桥 | 640×480、15 fps 的摄像头 MJPEG，通过现有 SSH 流到电脑。 | 实机取帧和预览通过。网桥 → 4G → 网桥三段均出画面，停止后摄像头释放。 |
| v27 4G | 320×240 JPEG，车端限制约 5 fps，逐张 HTTPS 上传，电脑轮询网关的最新帧。 | 实收约 4.3 fps。初次验收首画面约 13 秒，后续切换约 2 秒。用户实看反馈明显卡顿。 |
| v28 4G 低延迟 | 复用旧基线的 720p、20 fps 硬件 H.264，目标 1.2 Mbit/s、GOP 10，通过现有 HTTPS 入口连续分块推送和读取。 Windows 使用 PyAV 解码。 | 本地测试确认上传连接未结束时电脑可解码实机硬编码帧。ECS 新接口部署后，电脑通过 RK3588 的 4G 上传路径解码了 1280×720 的实机画面。 |

**怎么发现。** v27 的限帧、逐张图片请求和轮询共同限制画面更新。电脑侧 4G 网卡绑定访问云端 HTTPS 测试超时，所以当前 4G 图传指车端明确经蜂窝口上传，而电脑经自己的可用互联网接收。找回 7 月项目的配置后，在当前板端确认同款 Astra Pro 摄像头、硬编插件和硬件设备可用，并用相同的 720p、20 fps 和码率运行短探针。 [旧 TCP 中继背景](../deploy/ecs-relay/README.md) · [RK3588 编码代码](../deploy/three-link/h264_capture.py)

**怎么解决。** v28 把命令式 JPEG 轮询改为两条长连接，车端按序上传编码帧，ECS 按同一流转发，电脑解码后只保留最新的显示帧。车端输入队列只保留最新数据，定期发关键帧及解码参数。转发缓存有上限，积压时从新关键帧恢复，避免播放大量陈旧帧。电脑界面提供「Wi-Fi 网桥」与「4G 低延迟」，超过显示时效会提示画面中断。初次 ECS 安装失败，原因是安装器预期代理直接写在站点文件，而实际由 `/etc/nginx/snippets/yrt-mobile.conf` 引入。改为定位已包含的配置片段，测试通过后重新部署，保留原站点和其他入口。H.264 上传入口关闭 Nginx 请求缓冲，观看入口关闭响应缓冲，仍沿用 HTTPS 与角色令牌。 [Windows 预览](../deploy/three-link/video_view.py) · [H.264 中继](../deploy/mobile-gateway/h264_gateway.py) · [增量安装与回滚](../deploy/mobile-gateway/install-h264.py)

**当前验收。** Windows 桌面快捷方式指向 v28，操作顺序为「图传」→「4G 低延迟」→「开始预览」。已验证真实链路出画，不把编码目标当作已测得的公网帧率。接下来现场按用户的画面体验和操控手感验收。需要量化时，记录摄像头采集到屏幕的端到端延迟、持续显示帧率、最长停顿，以及 4G 弱网恢复和与控制流并发的表现。

## 6. 这轮留下的排查顺序

1. **先明确观测点。** 网口亮灯、DHCP 获得地址、SSH 可登录分别验证。发包提交、板端收包、手机展示也分别验证。视频首帧、连续播放和操控验收分别记录。
2. **每次只改一个影响结论的变量。** 校时问题用同机实验绕开两端时钟；无线问题用 UART 回环绕开射频；周期问题打散发送、换 USB 口、改读超时，再只重启一端。实验表同时保留方向、包长、发送间隔和实际收到量。
3. **先找已经跑通过的基线。** 旧项目的编码链为 v28 提供了比试探 JPEG 参数更直接的起点。重用已验证的硬编码和低积压策略，再根据现在的云端入口调整传输实现。
4. **发布以可复现材料为准。** 版本化代码、安装脚本、配置模板和非敏感实验统计可进仓库。板端、电脑、手机及 ECS 的实际令牌、密码、本机抓包和配置中的秘密值仅留各自设备。旧试验和首次验收的数量级不能替代移动、长时间与弱网复测。
